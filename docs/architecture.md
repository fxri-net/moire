# 架构设计

## 分层

```text
entries/          入口：装配实例、决定是否写全局、是否自动启动
  └─ kernel/      微内核：插件注册、依赖排序、通知通道、逆序卸载
       ├─ utils/      工具函数：无状态、不依赖内核
       ├─ i18n/       词条与插值：内置中英双语
       ├─ http/       请求封装：响应归一与钩子
       ├─ fields/     字段能力：16 种渲染器 + 字段/表单实例
       ├─ views/      视图能力：列表与表单装配、薄渲染
       └─ tools/      工具能力：页面动作 → 结构化结果
adapters/layui/   适配层：唯一允许触碰界面库的地方
schema/           声明契约：表单与列表的统一描述，不含 DOM
enums.ts          具名枚举：全部语义化 code
```

依赖方向单向向下：上层可以引用下层的类型与实现，下层不反向依赖上层。适配层之上没有任何模块直接引用 layui、jQuery、LayX、TinyMCE 或 Sortable——这条边界由 ESLint 的 `no-restricted-imports` 与 `no-restricted-globals` 强制，只有 `src/adapters/layui/**` 例外。

## 内核

内核只做四件事：注册、排序、装配、卸载。

### 注册与排序

- `use(plugin)` 按 `name` 登记，重名立即抛错。
- `start()` 按依赖拓扑排序后逐个装配：依赖优先，同层保持注册顺序。
- 依赖缺失与依赖成环都在装配前拦截，不会留下半装配的现场。

### 装配与隔离

- 装配即调用 `plugin.setup(context)`，插件通过 `context` 拿到版本号、通知函数、订阅入口与 `get(name)`。
- 单个插件 `setup` 抛错只发出通知，其余插件继续装配；这类失败不阻断启动。
- `dispose()` 按装配的逆序卸载，单个插件卸载失败同样只通知。

### 运行期追加

启动后再 `use`，内核会立即校验该插件的依赖并当场装配。启动后已无法重排既有插件的顺序，因此缺依赖时直接抛错，而不是静默失效。

### 通知通道

`context.notify` 与 `context.subscribe` 共用一条通道：插件与工具只负责发通知，呈现方式由业务侧订阅后决定。未订阅时通知不会落到任何界面上——默认实例把 `notify` 交给工具能力转发到适配层，其他场景按需订阅。

## 装配顺序

内置三个插件构成一条固定的依赖链：

```text
fields（无依赖） → views（depends: ['fields']） → tools（无依赖）
```

`views` 的表单装配依赖 `fields.createForm`，所以它声明 `depends: ['fields']`；`tools` 不依赖前两者，注册先后只影响同层顺序。

## 数据流

字段与视图都遵循「声明 → 装配 → 渲染」三段，装配阶段不碰 DOM：

```text
FormSchema / ListSchema
        │
        ├─ assemble：归一列与字段、排序、分页切片（纯函数，可单测）
        │
        └─ render：DOM 组装 + 适配层增强（只调 UiAdapter，不直接调界面库）
```

这样拆分的收益是可测：`views.list.assemble` 与 `views.form.assemble` 没有 DOM 依赖，排序、分页钳制、选择模式都能在 Node 环境直接断言。

## 状态归属

框架只托管「装配期需要共享」的状态：

| 状态                   | 归属                                  |
| ---------------------- | ------------------------------------- |
| 插件实例与装配顺序     | 内核                                  |
| 字段渲染器注册表       | `fields` 插件                         |
| 当前语言与词条副本     | `i18n` 实例                           |
| 列表当前页、排序、选择 | 业务侧（`assemble` 是纯函数，不缓存） |
| 业务数据与草稿         | 业务侧，框架不集中托管                |

0.4 中的 `shelf` / `store` / `cache` 一类运行态容器已移除，业务侧自持状态后再按需传参。

## 单一全局对象

传统页面只暴露一个 `window.moire`，入口内部固定执行「挂载 → 启动」：

```js
mountGlobal(moire).start()
```

ESM 入口只导出实例，不写全局、不自动启动，避免在模块环境里产生隐式副作用。两条入口共用同一份装配逻辑，差异只在最后一步。
