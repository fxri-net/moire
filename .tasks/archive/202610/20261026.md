# GitLab Pages 文档站基址改为项目名推导

延续 验收门禁与双平台流水线（见 archive/202610/20261025.md）。

计划位置：跨仓计划第 2 项；前置：无（按计划表顺序在另一仓之后执行）。

## 一、背景

同一宿主机上的另一个站点（另一仓库的项目）出现文档站样式 404：其 CI 把 `VITEPRESS_BASE` 默认值写成 GitLab 项目的完整路径，而自建实例的 Pages 只取项目名作子路径（`/<项目名>/`），前缀不一致导致 `index.html` 里的资源地址指向不存在的位置。

本仓当前没有暴露问题——`.gitlab-ci.yml` 里写死的 `/moire/` 恰好等于项目名。但写死值本身是同一类隐患：仓库改名、迁移分组或调整 Pages 路径后，站点会以同样的方式静默失效（构建通过、页面样式 404），且 `SITE_URL` / `REPO_URL` 未推导时 canonical、sitemap 与「编辑此页」回链也会指向旧位置。

## 二、实施方案

改 `.gitlab-ci.yml` 的 `pages` job：

- 去掉写死的 `VITEPRESS_BASE=/moire/`，改为按 `/$CI_PROJECT_NAME/` 推导。
- 同批把 `SITE_URL` / `REPO_URL` 改为按 `$CI_PAGES_URL` / `$CI_PROJECT_URL` 推导——三者同属「部署位置事实」，写死任一项都会在仓库改名或迁移后失真。
- `$CI_PAGES_URL` 不带尾斜杠，而 VitePress 的 sitemap / canonical 以 hostname 为基准做相对拼接，缺尾斜杠会吞掉末段路径（首页拼成 `…/moire`、内页拼成 `…/xxx.html`）。故 `SITE_URL` 写成 `${CI_PAGES_URL%/}/` 补齐尾斜杠（已有尾斜杠时同样成立）。
- 继续保留 CI/CD 变量覆盖能力：三者统一用 `${VAR:-默认值}` 形式，平台侧同名变量仍优先。
- 同步文件头第 4-5 行注释，描述改成推导口径。

`docs/.vitepress/config.mts` 不改：其默认 `base`（`/moire/`）是给 GitHub Pages 的回落值，GitLab 侧由 `VITEPRESS_BASE` 覆盖；`.github/workflows/deploy-docs.yml` 已显式注入三个变量，不受影响。

## 三、影响范围

`.gitlab-ci.yml` 的 `pages` job（文档站构建入参与产物路径），以及文件头说明注释。不改源码、不改 `.github/workflows/deploy-docs.yml`、不改 `pnpm verify` 校验链。

## 四、验证方式

- `pnpm verify` 全绿（其中已含文档站构建步骤，构建即做站内死链检查）。
- 以 `VITEPRESS_BASE=/moire/ pnpm docs:build` 构建，检查 `docs/.vitepress/dist/index.html` 中资源前缀仍为 `/moire/assets/...`（与改动前一致，证明推导值与写死值等价）。
- 推送后在线上抓站点首页 HTML，确认前缀未变、CSS 返回 200（推送需单独确认）。

## 五、回滚方案

只改一个 CI 配置文件，`git revert` 对应提交即可恢复写死基址，无状态迁移、无产物依赖。

## 六、实施结果

- `.gitlab-ci.yml`：`pages` job 去掉写死基址，改为三行 `export`（`VITEPRESS_BASE` 取 `/$CI_PROJECT_NAME/`、`SITE_URL` 取 `${CI_PAGES_URL%/}/`、`REPO_URL` 取 `$CI_PROJECT_URL`）后执行 `pnpm docs:build`，均保留平台变量覆盖；文件头注释同步为推导口径。
- 未改 `docs/.vitepress/config.mts` 与 `.github/workflows/deploy-docs.yml`。

验证：`pnpm verify` 全绿（含文档站构建与站内死链检查）；按线上口径注入三个变量后重建，`docs/.vitepress/dist/index.html` 资源前缀为 `/moire/assets/...`，`sitemap.xml` 的 `<loc>` 为 `https://***:444/moire/...`，与改动前的输出等价。线上首轮部署需推送后观察，属验收边界。

## 20261025-唐启云-产物清单记录源码提交

# 产物清单记录源码提交

## 计划位置

前七批工程化改造与文档站、双平台流水线之后的独立增强；方案经确认取「保持 dist 分支 + 标签打在产物提交」的形态，补溯源能力。

## 背景

产物经 `dist` 孤儿分支按 `vX.Y.Z` 标签交付，标签指向产物提交而非 main 提交，因此从产物侧无法得知它由哪个源码提交构建。`manifest.json` 目前只记 `version` 与 `builtAt`，缺少源码提交这一项；`--skip-build` 时也没有任何机制拦住「拿上一次构建的产物发布」。

## 实施方案

1. `scripts/manifest.mjs`：清单增加 `commit` 字段，取 `git rev-parse HEAD`；取不到 git（源码包解压等场景）时写空串并告警，不阻断构建。
2. `scripts/release.mjs`：`verifyManifest` 增加一条校验——`manifest.commit` 必须等于当前 `HEAD`，不一致即报错，避免发布旧产物。
3. 文档同步：`docs/distribution.md` 的分发形态与校验产物章节补 `commit` 字段；`docs/release.md` 的出产物步骤补这条校验。

## 影响范围

- 修改：`scripts/manifest.mjs`、`scripts/release.mjs`、`docs/build.md`、`docs/distribution.md`、`docs/release.md`、`docs/migration.md`
- `dist/manifest.json` 结构新增 `commit` 字段，从下次发版起生效；已发布的 1.0.0 清单无该字段
- 不改运行期代码、类型声明、分发方式与标签形态

## 验证

- `pnpm build` 后核对 `dist/manifest.json` 的 `commit` 与 `git rev-parse HEAD` 一致
- `pnpm verify` 全量通过
- `toolkit tasks check` 通过

## 完成情况

- `scripts/manifest.mjs` 新增 `sourceCommit()`，清单在 `version` 与 `builtAt` 之间写入 `commit`；无 git 环境写空串并告警
- `scripts/release.mjs` 的 `verifyManifest` 增加 HEAD 一致性校验，不一致时报错并提示重新构建
- `docs/build.md`：产物表、构建步骤描述、清单结构样例与说明段同步 `commit`
- `docs/distribution.md`：分发形态与校验产物章节补 `commit` 的溯源用途
- `docs/release.md`：出产物校验步骤补「源码提交等于当前 HEAD」
- `docs/migration.md`：产物差异表补 `commit`
